## 3.2 Cálculo de Totales (fórmula EXACTA)
- **Precios SIN IGV** (los precios unitarios se ingresan sin impuesto).
- **Subtotal del ítem** = `(quantity * unit_price) - discount_item`.
- **IGV del ítem** = `subtotal_item * 0.18` (redondeo a 2 decimales).
- **Total del ítem** = `subtotal_item + iva_item`.
- **Subtotal cabecera** = Σ `subtotal` de ítems + Σ `amount_without_iva` de third_party_orders (las OC de terceros se cargan sin IGV, ver entidades).
- **Descuento cabecera**: campo `discount` (monto fijo S/) o `discount_type` (porcentaje). Si `discount_type` es %, se convierte a monto: `discount = round(subtotal * discount_type / 100, 2)`. El `discount` ALMACENADO es SIEMPRE el monto en soles.
- **IGV cabecera** = `(subtotal - discount) * 0.18`.
- **Total cabecera** = `subtotal - discount + iva`.
- Redondeo: `round(..., 2)` en cada paso. Almacenar decimal(12,2).
- El cálculo se realiza en el Service (NO en el controlador, NO en JS del cliente como fuente de verdad). El backend recalcula SIEMPRE.

## 3.3 Flujo de Estados (Workflow)
Estados exactos del Presupuesto (`.clinerules/01-flujo-taller.md`):
- `draft` → Borrador
- `sent_insurance` → En aprobación seguro (se envía a la aseguradora)
- `approved_insurance` → Aprobado seguro
- `rejected_insurance` → Rechazado seguro
- `sent_client` → En aprobación cliente
- `approved_client` → Aprobado cliente
- `rejected_client` → Rechazado cliente
- `in_repair` → En reparación
- `finalized` → Finalizado

Transiciones permitidas (validar en Service/Policy, prohibido saltarse):
- Solo `draft` puede → `sent_insurance` o `sent_client`.
- `sent_insurance` → `approved_insurance` | `rejected_insurance`.
- `sent_client` → `approved_client` | `rejected_client`.
- `approved_insurance` o `approved_client` → `in_repair`.
- Cualquier estado activo (no finalizado/rechazado) → regresar a `draft` (para correcciones) SIEMPRE que no tenga WorkOrder asociada (módulo futuro; validar solo que no haya OT).
- `in_repair` → `finalized`.
- Estados terminales: `finalized`, `rejected_insurance`, `rejected_client`.
- Acciones del controlador: métodos `sendToInsurance()`, `approveInsurance()`, `rejectInsurance()`, `sendToClient()`, `approveClient()`, `rejectClient()`, `startRepair()`, `finalize()` con rutas POST dedicadas, estilo `check-ins/{checkIn}/approve` (ver sección 5.1).

## 3.4 Regla de Sincronización de Ítems (diff/upsert) — OBLIGATORIO
PROHIBIDO el patrón "borrar todo y volver a insertar" (`.clinerules/06`).
En `EstimateService` implementar `syncItems(Estimate $estimate, array $items)`:
```php
// Pseudocódigo patrón (ver CheckInService::syncDamages como referencia real):
$existing = $estimate->items()->get()->keyBy('id');

foreach ($items as $item) {
    if (empty($item['description']) && empty($item['unit_price']) && empty($item['type'])) {
        continue; // fila vacía
    }
    $id = $item['id'] ?? null;
    if ($id && isset($existing[$id])) {
        $existing[$id]->update([...]);
        $existing->forget($id);
    } else {
        $estimate->items()->create([...]);
    }
}

// Eliminar solo los que ya no vienen (soft delete)
foreach ($existing as $item) {
    $item->delete();
}
```

- Toda la operación (cabecera + items + OC + franquicia) dentro de `DB::transaction()`.
- Recibirá el request como `items[]` (array de filas con `id` opcional para edición).
- Aplicar el MISMO patrón diff/upsert para `third_party_orders` (syncThirdPartyOrders) y para `franchise_calculation` (updateOrCreate por estimate_id).

- `establishment_id` por defecto: `Auth::user()?->establishment_id` (idéntico a CheckInService::create).
- `created_by`/`updated_by` = `Auth::id()`.
- Si `number === null` (serie tipo API): guardar `document_number` = null y lanzar/omitir según el flujo (mismo manejo que CheckInService::assignDocumentNumber).
- La numeración solo aplica en CREATE. En UPDATE no se renumera.

## 3.6 Campos de cabecera (edición)
- `hourly_rate` y `panel_rate`: permitido sobreescribir por presupuesto (el modelo `Estimate` tiene sus propios valores). El formulario puede precargarlos desde `insurance_hourly_rate`/`insurance_panel_rate` de la aseguradora seleccionada, pero el usuario siempre puede editarlos.

6. RELACIONES CLAVE PARA ESTE MÓDULO

## 6.1 Presupuesto ↔ CheckIn (inventario)
- `estimate.check_in_id` nullable → `check_ins.id`.
- Un presupuesto puede crearse "desde" un CheckIn aprobado (recomendado: en `create()` aceptar query param `?check_in_id=...` y precargar `vehicle_id`, `client_id`, `insurance_company_id`, `claim_number` desde el inventario).
- Relación Eloquent en Estimate: `checkIn()` belongsTo(CheckIn::class). En CheckIn: `estimates()` hasMany(Estimate::class) (añadir al modelo CheckIn).
- NO es obligatorio que exista CheckIn previo: `check_in_id` nullable (presupuesto directo).

## 6.2 Relaciones Eloquent a definir en Estimate
- `vehicle()` belongsTo(Vehicle::class)->withTrashed() (patrón CheckIn)
- `client()` belongsTo(Party::class, 'client_id')
- `insuranceCompany()` belongsTo(Party::class, 'insurance_company_id')
- `establishment()` belongsTo(Establishment::class)
- `advisor()` belongsTo(User::class, 'advisor_id')
- `checkIn()` belongsTo(CheckIn::class)
- `documentSeries()` belongsTo(DocumentSeries::class)
- `items()` hasMany(EstimateItem::class)->orderBy('sort_order')
- `thirdPartyOrders()` hasMany(ThirdPartyOrder::class)
- `franchiseCalculation()` hasOne(FranchiseCalculation::class)
- `creator()` / `updater()` belongsTo(User::class, 'created_by'/'updated_by')
- Accessor `getStatusLabelAttribute()` con STATUS_LABELS (mismo patrón CheckIn).
- Accessor `getFormattedDocumentNumberAttribute()` → `$this->document_sn`.

## 6.3 Actividad (activitylog)
- Modelo Estimate: `LogsActivity` + `getActivitylogOptions()` con `->logOnly([...columnas relevantes...])->logOnlyDirty()->dontSubmitEmptyLogs()->useLogName('estimate')`. Mismo patrón que CheckIn/Vehicle.

7. (OPCIONAL) REGLAS DE VALIDACIÓN ADICIONALES EXISTENTES
- CheckInRequest ya tiene: aseguradora debe ser `is_insurance_company = true` (validación custom con Closure). Replicar en EstimateRequest.
- Convención general: `nullable` + `integer` + `exists` para FKs opcionales; `required` para FKs obligatorias.
- Fechas: `nullable|date`. No hay regla "fecha no pasada" en el proyecto actualmente.
- Identidad de documento: `document_number` es `unsignedInteger` (no string). El `document_sn` es la clave de búsqueda.
